# 图片字节拆分独立 store，消除整份文档重写

## 背景

图片以 Base64 内联在 `ProjectDocument.assets[].items[].images[].data`，因此**每加一张照片都要把整份项目文档重写一遍**（写放大 O(n²)）。用户库已达 381MB，单个项目文档可达上百 MB。

由此产生的现场事故（均有代码证据）：

| 现象 | 路径 | 状态 |
|---|---|---|
| 拍着拍着卡死、"保存中"长时间转圈 | 整份文档 JSON 序列化 + 结构化克隆在主线程 | 未修 |
| 拍完关窗口，照片没了 | `AppContext.tsx` debounce 500ms + 卸载 flush 都是"发起后不等待"的异步写；无 `beforeunload` 拦截；大文档写十几秒，页面销毁即事务中止 | 未修 |
| 手机上传的图被电脑端覆盖 | 电脑端刚打开项目的时序窗口内，手机走 `saveLanImageToProject` 直写库，电脑端内存仍是旧文档，下次自动保存整份覆盖冲掉 | 未修 |
| 保存超时被误判失败 | v0.6.2 已把整份文档读写超时放宽到 `DB_DOC_TIMEOUT_MS`(120s)，属缓解 | 缓解 |
| 丢了哪张图查不出来 | 图片是文档内数组元素，缺失不留痕迹，无可对账清单 | 未修 |

v0.6.0~v0.6.2 修的是列表加载卡死、升级中止、摘要漂移与静默失败可见化，**均未触及本根因**。

## 目标

把图片字节从项目文档中拆出，存入独立 `images` store，文档只保留引用。使"新增一张图"的写入量与项目已有图片数量无关。

## 需求

### R1 存储模型
- 新增 `images` store：主键 `${projectId}:${imageId}`，字段至少 `id / projectId / imageId / data / fileName / mimeType / byteSize / createdAt`；建 `projectId` 索引以便按项目批量取用与删除。
- `ProjectDocument` 中的 `images[]` 元素改为引用（保留 `id / fileName / caption / uploadedAt` 等元数据，去掉 `data`）。
- 新增图片 = 只写一条 images 记录 + 一次轻量文档更新（不再重写全部字节）。

### R2 迁移（DB_VERSION=5）
- `onupgradeneeded` 只建表建索引，**不得遍历数据**（v0.6.0 事故教训：遍历异常会中止 versionchange 并回滚版本）。
- 存量内联图片的搬迁在升级后异步执行，且必须：**可中断续跑**（按项目分批、记录进度）、**单个项目失败不影响其他项目**、**失败可回退**（搬迁完成前不删除文档内原始 `data`）。
- 迁移期间应用可正常使用；读取路径需同时兼容"已搬迁（引用）"与"未搬迁（内联）"两种形态。

### R3 并发与丢失防护
- 图片写入不再依赖整份文档覆盖，消除"手机上传被电脑端覆盖"的竞态。
- 关窗/切项目时的最后一次保存必须有可靠兜底（图片已独立落库，文档元数据写入量小到可在卸载窗口内完成）。

### R4 完整性对账
- 存储自检扩展：文档引用的图片数 vs `images` store 实际记录数，缺失可报出"某项目缺 N 张图（含 imageId）"。
- 结果并入诊断包与存储设置面板。

### R5 全链路覆盖
下列路径全部改为走新模型，且桌面端与网页版同步验证：
- 电脑端拍照/选文件、网页相机
- 手机局域网上传（`lanImageSink` / `App.tsx` 分流）
- 数据包导入导出（`exportImport`，含 `.evidence` 加密包）
- Word 报告生成（须保持原分辨率内嵌，见约束）
- 存量图片压缩瘦身

## 约束

- 不得降低导出报告的图片分辨率（现有约束：报告内嵌完整分辨率，用户会对比清晰度验收）。
- CSP 为 `connect-src 'self'`，data URL ↔ Blob 转换必须用 `atob`/`FileReader`，禁止 `fetch(data:)`。
- DB 版本一旦发布不可降级；迁移必须在 381MB 量级的真实数据上可完成。
- 删除项目/项目组时必须同事务清理其 images 记录，否则产生孤儿字节占用空间。

## 验收标准

- [ ] 新增一张图片的写入耗时与该项目已有图片数**无关**（可量化：50 张图的项目与 5 张图的项目，单张写入耗时同量级）
- [ ] 拍照后立即关闭窗口，重新打开该图片仍在
- [ ] 手机上传与电脑端并发操作同一项目，两侧改动均不丢失
- [ ] 381MB 量级存量库可完成迁移；迁移中途强制关闭应用后重启能继续，数据不丢
- [ ] 迁移完成前后，Word 报告导出的图片分辨率与现状一致
- [ ] 存储自检能报出"文档引用了但实际缺失"的图片
- [ ] 数据包导入导出、加密包往返、存量压缩在新模型下全部通过
- [ ] 桌面客户端（exe）与网页版均实测通过
- [ ] 新增/更新的 verify 脚本全绿，`npm run build` 通过
